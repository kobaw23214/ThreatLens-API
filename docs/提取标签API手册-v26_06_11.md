# NER API 接口调用手册 v1.4.0

## 1. 概述

本 API 提供基于深度学习的命名实体识别（NER）服务，支持中文和英文文本的实体提取。采用异步处理模式：

1. **提交任务**：提交文本和标签，获取 `task_id`
   - **JSON 方式** (`POST /extract`)：适合短文本，单次最多 50,000 字符（可配置）
   - **文件上传** (`POST /extract/upload`)：适合长文档，支持 10 MB 以内的 `.txt / .md / .csv / .json` 等纯文本文件
2. **查询结果**：使用 `task_id` 查询提取结果
3. **回调推送**（可选）：任务完成后自动将结果推送到指定地址，无需轮询

**核心能力**：
- 自动长文本分块：超出模型 token 上限的文本会被自动切成若干 Chunk 独立推理，再合并去重，解决 tokenizer 静默截断问题
- 结果复用缓存：相同输入在同一模型 + 同参数下直接复用历史结果
- 文本输入与文件上传共享同一缓存：内容相同即可互相命中
- 任务完成回调：失败不会自动重试，失败记录可手动重试
- **MITRE ATT&CK 技战术识别**：内置 `tram`（SciBERT 分类器，英文）与 `attack-llm`（大模型映射，中英文）两个 `attack` 类模型，从威胁报告文本中识别 ATT&CK 技术，默认「全量」提取，也可按技术编号 / 战术过滤，详见[模型列表](#7-获取模型列表)

---

## 2. 基础信息

- **Base URL**: `http://your-server:8036`
- **Content-Type**: `application/json`
- **字符编码**: UTF-8
- **请求方式**: POST / GET

## 3. 用户认证

为保障服务安全并限制调用额度，本 API 的大部分接口都需要进行身份认证。系统提供两种认证方式，任选其一即可，二者都会解析出调用所属的用户账户（用于限额与用量统计）：

| 认证方式 | 请求头 | 适用场景 |
|----------|--------|----------|
| **API Key** | `X-API-Key: ner_xxxxx` | 脚本、自动化、第三方系统集成（推荐） |
| **JWT Bearer Token** | `Authorization: Bearer <token>` | Web 前端、临时交互 |

> **认证优先级**：后端先检查 `Authorization: Bearer`，再检查 `X-API-Key`，两者都没有则返回 **401**。
>
> **关闭认证**：当后端 `.env` 设置 `AUTH_ENABLED=false` 时，所有接口都免认证访问（内部以一个虚拟 admin 账户身份运行，且不做限额）。默认 `AUTH_ENABLED=true`。

### 3.1. 认证方式一：API Key（推荐，用于脚本与三方集成）

在 HTTP 请求头中携带 `X-API-Key` 即可。API Key 可在 Web 管理界面的用户面板创建 / 吊销，也可通过下方的 `/auth/api-keys` 接口管理，支持设置独立的过期天数。该 Key 消耗的额度计入其所属账户的总限额。

- **Header 键名**：`X-API-Key`
- **Header 值**：你的 API Key（形如 `ner_a2b3c4d5...`）

```bash
curl -X POST "http://your-server:8036/extract" \
  -H "X-API-Key: ner_your_api_key_here" \
  -H "Content-Type: application/json" \
  -d '{
    "text": "张三在北京创办了一家科技公司。",
    "labels": ["人物", "地点"]
  }'
```

### 3.2. 认证方式二：用户名密码（JWT）（适用于 Web 与临时交互）

先调用登录接口用用户名 + 密码换取 JWT Access Token，再在后续请求头里带上该 Token。Token 默认有效期 24 小时（由 `JWT_EXPIRE_HOURS` 控制）。

**第一步：登录获取 Token**

- **URL**：`POST /auth/login`
- **Content-Type**：`application/json`

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| `username` | string | 是 | 用户名 |
| `password` | string | 是 | 密码 |

请求示例：

```json
{
  "username": "your_username",
  "password": "your_password"
}
```

响应示例（HTTP 200）：

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.your_token_data.signature",
  "token_type": "bearer",
  "user": {
    "id": 2,
    "username": "your_username",
    "is_admin": false,
    "limit_5h": 2000,
    "limit_weekly": 100000,
    "is_active": true
  }
}
```

> 用户名或密码错误返回 **401**；账户被停用返回 **403**。

**第二步：携带 Token 调用接口**

- **Header 键名**：`Authorization`
- **Header 值**：`Bearer <你的_access_token>`

```bash
curl -X POST "http://your-server:8036/extract" \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..." \
  -H "Content-Type: application/json" \
  -d '{
    "text": "张三在北京创办了一家科技公司。",
    "labels": ["人物", "地点"]
  }'
```

### 3.3. 哪些接口需要认证

| 类别 | 接口 | 是否需要认证 |
|------|------|--------------|
| 实体提取 | `POST /extract`、`POST /extract/upload` | ✅ 需要（且计入调用限额） |
| 任务查询 | `GET /tasks`、`GET /tasks/{task_id}`、`GET /tasks/{task_id}/result`、删除任务 | ✅ 需要 |
| 统计 | `GET /stats` | ✅ 需要 |
| 回调管理 | 所有 `/callback/failed`、`/callback/retry`、`/callback/resolve`、`/callback/success`、`/callback/stats`、`/callback/test` | ✅ 需要 |
| 账户 / 个人中心 | `GET /auth/me`、`POST /auth/change-password`、`/auth/api-keys` 系列 | ✅ 需要 |
| 管理员 | 所有 `/admin/*` | ✅ 需要（且要求管理员权限） |
| 登录 | `POST /auth/login` | ❌ 公开 |
| 模型 / 服务信息 | `GET /models`、`GET /server-info` | ❌ 公开 |
| 实时状态 | `GET /events`（SSE） | ❌ 公开 |
| 可视化嵌入 | `GET /iframe/{task_id}` | ❌ 公开 |

> **数据可见性**：普通用户只能查询 / 统计自己提交的任务和回调记录；管理员可通过 `user_id` 查询参数查看指定用户或全局的数据。

### 3.4. 调用限额

每个账户都有两档调用限额，**仅对 `POST /extract` 和 `POST /extract/upload` 生效**（这两个接口每次成功调用都会记录用量）：

| 限额 | 字段 | 默认值 | 说明 |
|------|------|--------|------|
| 5 小时限额 | `limit_5h` | 2000 | 滚动 5 小时窗口内最大调用次数 |
| 每周限额 | `limit_weekly` | 100000 | 滚动 7 天窗口内最大调用次数 |

- 任一限额设为 `0` 表示该维度**无限制**。
- 超出限额时返回 **429 Too Many Requests**，`detail` 会说明已用 / 上限，如 `5小时调用次数已达上限 (2000/2000)，请稍后再试`。
- 可通过 `GET /auth/me` 查看当前用量。

### 3.5. 认证与账户管理接口

除了在管理界面操作，系统还提供以下接口（前缀 `/auth` 为登录用户自助，前缀 `/admin` 仅管理员）。

**个人中心（前缀 `/auth`，需认证）**

| 方法与路径 | 说明 |
|------------|------|
| `POST /auth/login` | 用户登录获取 Access Token（公开，无需认证） |
| `GET /auth/me` | 获取当前用户信息及限额使用统计 |
| `POST /auth/change-password` | 修改当前用户密码，请求体 `{"old_password": "...", "new_password": "..."}`（新密码至少 6 位） |
| `GET /auth/api-keys` | 查询当前用户的所有 API Key |
| `POST /auth/api-keys` | 创建新 API Key，请求体 `{"name": "Key名称", "expires_days": 30}`（`expires_days` 范围 1-365）。**完整 Key 仅在此次响应中返回一次，请妥善保存** |
| `DELETE /auth/api-keys/{key_id}` | 吊销指定 ID 的 API Key |

> 创建 API Key 的响应示例：
> ```json
> {
>   "id": 3,
>   "key": "ner_a2b3c4d5e6f7...（完整 Key，仅此一次可见）",
>   "key_prefix": "ner_a2b3c4d",
>   "name": "我的脚本",
>   "expires_at": "2026-07-11T10:00:00+08:00"
> }
> ```

**后台用户管理（前缀 `/admin`，仅管理员）**

| 方法与路径 | 说明 |
|------------|------|
| `GET /admin/users` | 分页列出所有用户 |
| `POST /admin/users` | 创建新用户，请求体 `{"username": "...", "password": "...", "limit_5h": 2000, "limit_weekly": 100000}`（用户名 2-50 位，密码至少 6 位） |
| `PUT /admin/users/{user_id}` | 修改用户（可改密码、限额、`is_active` 启停状态） |
| `DELETE /admin/users/{user_id}` | 删除指定用户（管理员账户不可删除） |
| `GET /admin/users/{user_id}/api-keys` | 查看指定用户的 API Key 列表 |
| `POST /admin/users/{user_id}/api-keys` | 为指定用户创建 API Key |
| `GET /admin/usage-stats` | 分页查看全局所有用户的调用用量统计 |

## 4. 接口列表

### 4.1. 提交实体提取任务（JSON）

提交文本和标签，创建实体提取任务。适用于短文本（默认 ≤ 50,000 字符）。

> **长文本场景请使用** [`POST /extract/upload`](#2-上传文本文件提取实体)。两个接口共享同一套缓存机制（`task_hash` 基于文本内容本身），不管用哪种方式提交，只要文本解码后字节相同 + 其它参数相同，都可以互相命中缓存。

#### 4.1.1. 请求信息

- **URL**: `/extract`
- **Method**: `POST`
- **Content-Type**: `application/json`

#### 4.1.2. 请求参数

| 参数名 | 类型 | 必填 | 默认值 | 说明 |
|--------|------|------|--------|------|
| `text` | string | 是 | - | 待提取实体的文本。长度上限由 `MAX_TEXT_LENGTH` 环境变量控制，默认 50,000 字符。超出时返回 413，提示改用 `/extract/upload`。 |
| `labels` | array[string] | 是 | - | 实体类型列表，支持中文标签，如 `["人物", "地点", "机构"]` |
| `label_mapping` | object | 否 | null | 标签映射字典，将原始标签映射为标准标签，如 `{"人物": "PERSON"}` |
| `model_name` | string | 否 | 自动选择 | 指定使用的模型名称，可选值见[获取模型列表](#7-获取模型列表) |
| `reuse_cache` | boolean | 否 | false | 是否启用结果复用，相同 `(text, labels, model, chunk_cfg)` 会复用历史结果 |
| `information_json` | object | 否 | `{}` | 用户自定义信息，会在结果中原封不动返回，用于消息绑定 |
| `callback` | object | 否 | null | 回调配置，任务完成后自动推送结果到指定地址，详见下方说明 |
| `chunk_enabled` | boolean | 否 | 后端 `CHUNK_ENABLED` | 是否启用长文本自动分块。默认 `true`。关闭后整段文本直接送模型(超过 tokenizer 上限会被静默截断)。|
| `chunk_overlap` | integer | 否 | 后端 `CHUNK_OVERLAP`(默认 32) | 相邻 Chunk 之间的字符重叠数,范围 `[0, 512]`。用于避免实体被切在边界上。|
| `chunk_safety_margin` | integer | 否 | 后端 `CHUNK_SAFETY_MARGIN`(默认 16) | `effective_max_tokens = model_max_tokens − labels_token_count − safety_margin`,范围 `[0, 64]`。|
| `threshold` | float | 否 | 后端 `CHUNK_THRESHOLD`(默认 0.5) | 送入 `predict_entities` 的阈值,范围 `[0.0, 1.0]`。越高越严格。|

> **分块参数说明**:四个分块字段都是可选的。留空时使用后端 `.env` 的 `CHUNK_*` 默认值;提供时,**参数本身会纳入 `compute_task_hash`**,即不同参数对应不同缓存记录。
>
> 越界参数会直接返回 HTTP 422;`labels_token_count + safety_margin >= model_max_tokens`(即 `effective_max_tokens <= 0`)会把任务标记 `failed`。

#### 4.1.3. callback 参数结构

| 参数名 | 类型 | 必填 | 默认值 | 说明 |
|--------|------|------|--------|------|
| `url` | string | 是 | - | 回调地址，必须是 http/https URL |
| `method` | string | 否 | `POST` | HTTP 方法，支持 `POST` / `PUT` |
| `headers` | object | 否 | null | 自定义请求头，如 `{"Authorization": "Bearer xxx"}` |
| `timeout` | integer | 否 | 30 | 超时时间（秒），范围 1-300 |

#### 4.1.4. 请求示例

```json
{
  "text": "张三在北京创办了一家科技公司，主要研发人工智能产品。",
  "labels": ["人物", "地点", "机构", "产品"],
  "label_mapping": {
    "人物": "PERSON",
    "地点": "LOCATION",
    "机构": "ORG",
    "产品": "PRODUCT"
  },
  "model_name": "gliner_multi-v2.1",
  "reuse_cache": false,
  "information_json": {
    "file_id": "0537ef0d8ac6a2179a58067615825924",
    "user_id": "12345",
    "request_time": "2026-04-30 10:00:00"
  }
}
```

#### 4.1.5. 带回调的请求示例

```json

```

#### 4.1.6. 响应参数

| 参数名 | 类型 | 说明 |

### 4.2. 上传文本文件提取实体

通过 `multipart/form-data` 上传纯文本文件进行实体提取。**适用于长文档**——单文件最大 10 MB（约 200 万汉字 UTF-8）。

#### 4.2.1. 请求信息

- **URL**: `/extract/upload`
- **Method**: `POST`
- **Content-Type**: `multipart/form-data`

#### 4.2.2. 表单字段

| 字段名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| `file` | file | 是 | 纯文本文件（`.txt / .md / .csv / .json / .log / .xml / .yaml` 等）。单文件上限由 `UPLOAD_MAX_BYTES` 控制，默认 10 MB |
| `labels` | string (JSON) | 是 | 实体标签 JSON 数组字符串，如 `'["人物","地点"]'` |
| `model_name` | string | 否 | 同 `/extract` |
| `label_mapping` | string (JSON) | 否 | 同 `/extract`，需 JSON 字符串形式 |
| `reuse_cache` | boolean | 否 | 同 `/extract` |
| `information_json` | string (JSON) | 否 | 同 `/extract`，需 JSON 字符串形式 |
| `callback` | string (JSON) | 否 | 同 `/extract`，需 JSON 字符串形式 |
| `chunk_enabled` | boolean | 否 | 同 `/extract` |
| `chunk_overlap` | integer | 否 | 同 `/extract` |
| `chunk_safety_margin` | integer | 否 | 同 `/extract` |
| `threshold` | float | 否 | 同 `/extract` |

> **为什么某些字段是 JSON 字符串**：`multipart/form-data` 的每个 part 只能传字符串或文件，没有原生数组/对象类型。所以 `labels` / `label_mapping` / `information_json` / `callback` 这些在 JSON 接口里是原生对象的字段，在上传接口里必须序列化为 JSON 字符串。前端 UI 已自动处理该差异，调用方直接手写 curl 时需要注意。

#### 4.2.3. 文件校验四道防线

文件会经过以下校验，任一失败都会返回 HTTP 400：

1. **非空 & 大小限制**：空文件或超过 `UPLOAD_MAX_BYTES` 的拒绝
2. **扩展名白名单**：仅允许 `UPLOAD_ALLOWED_EXTENSIONS` 中列出的扩展名（默认 `.txt / .md / .markdown / .rst / .log / .csv / .tsv / .json / .jsonl / .ndjson / .xml / .yaml / .yml / .ini / .cfg / .toml / .html / .htm / .srt / .vtt`）
3. **二进制特征检测**：头 4 KB 出现 NULL 字节或非打印控制字符占比 > 30%，视为二进制文件拒绝。即使把 PNG 重命名为 `.txt` 也会被识别
4. **编码自动识别**：依次尝试 UTF-8（含 BOM）→ UTF-16（含 BOM）→ GB18030 → Latin-1，失败则 400

解码后的文本会直接替代 JSON 接口里的 `text` 字段，继续走完全相同的分块推理 / 缓存 / 回调流程。

#### 4.2.4. 请求示例

```bash
# 基础用法
curl -X POST "http://localhost:8036/extract/upload" \
  -F "file=@doc.txt" \
  -F 'labels=["人物","地点","机构","时间"]' \
  -F "model_name=gliner-x-large"

# 完整参数
curl -X POST "http://localhost:8036/extract/upload" \
  -F "file=@report.md" \
  -F 'labels=["人物","地点"]' \
  -F 'label_mapping={"人物":"PERSON","地点":"LOCATION"}' \
  -F "model_name=gliner_multi-v2.1" \
  -F "reuse_cache=true" \
  -F 'information_json={"file_id":"abc123"}' \
  -F "chunk_overlap=64" \
  -F "threshold=0.6" \
  -F 'callback={"url":"https://api.example.com/cb","timeout":30}'
```

#### 4.2.5. 响应

响应格式与 [`POST /extract`](#1-提交实体提取任务json) 完全一致（同一个 `ExtractResponse` schema）。

#### 4.2.6. 错误示例

```json
// 400 — 空文件
{ "detail": "上传文件为空" }

// 400 — 扩展名不支持
{ "detail": "不支持的文件类型 '.docx'。仅支持纯文本格式: .cfg, .csv, .htm, .html, .ini, .json, ..." }

// 400 — 二进制内容
{ "detail": "文件内容看起来不是纯文本(检测到二进制特征),请上传真实文本文件" }

// 400 — 超过大小上限
{ "detail": "上传文件过大 (11534336 字节),上限 10485760 字节" }

// 422 — labels 字段不是合法 JSON
{ "detail": "表单字段 labels 不是合法 JSON: Expecting value (pos 0)" }
```

#### 4.2.7. 关联接口：上传邮件(.eml / .msg)提取 IOC

> 完整的文件格式支持、解析方式与集成示例见《文件解析手册》。

- **URL**: `/extract/eml`
- **Method**: `POST`
- **Content-Type**: `multipart/form-data`

上传 `.eml` / `.msg` 邮件文件：`.eml` 用 [mail-parser](https://github.com/SpamScope/mail-parser)、`.msg`(Outlook OLE2)用 [extract-msg](https://github.com/TeamMsgExtractor/msg-extractor) 解析为同结构的邮件 JSON（头部 / Received 逐跳链路 / 正文 / 附件元数据），再把关键字段展平为文本走异步队列做 IOC 提取。与 `/extract/upload` 的差异：

- 仅接受 `.eml` / `.msg` 扩展名；`labels` 可留空，默认使用内置 IOC 标签集（`邮箱/域名/URL/IP/IPv6/MD5/SHA1/SHA256/SHA512/CVE/比特币地址/MAC地址/文件路径/CIDR/ASN`）
- `model_name` 默认 `ioc-finder`（确定性 IOC 引擎，类型覆盖最全）
- 解析出的完整邮件 JSON 存入 `information_json.eml`，随 `/tasks/{id}/result` 一并返回（`format` 字段标识 `eml` / `msg`）

| 字段名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| `file` | file | 是 | `.eml` / `.msg` 邮件文件，大小上限同 `UPLOAD_MAX_BYTES`（默认 10 MB） |
| `labels` | string (JSON) | 否 | 实体标签 JSON 数组字符串，留空用内置 IOC 标签集 |
| `model_name` | string | 否 | 默认 `ioc-finder` |
| `reuse_cache` | boolean | 否 | 同 `/extract` |
| `information_json` | string (JSON) | 否 | 同 `/extract`；服务端会注入 `eml` 键存放邮件解析 JSON |
| `callback` | string (JSON) | 否 | 同 `/extract` |

`information_json.eml` 结构（附件 payload 已剥离，仅保留元数据与哈希）：

```json
{
  "eml": {
    "format": "eml",
    "filename": "phishing.eml", "eml_sha256": "…",
    "subject": "…", "from": [["显示名", "a@b.com"]], "to": [], "cc": [], "reply_to": [],
    "date": "2020-04-21T14:05:44+00:00", "timezone": "+5.0", "message_id": "…",
    "headers": { "Received": "…", "Authentication-Results": "…" },
    "received": [ { "hop": 1, "from": "[192.168.0.4]", "by": "mail.example.com", "with": "ESMTP", "date_utc": "…" } ],
    "to_domains": ["example.com"],
    "body": "…", "text_plain": [], "text_html": [],
    "attachments": [ { "filename": "invoice.pdf", "mail_content_type": "application/pdf", "size": 12345, "sha256": "…" } ],
    "has_defects": false, "defects": []
  }
}
```

请求示例：

```bash
curl -X POST "http://localhost:8036/extract/eml" \
  -F "file=@phishing.eml"

# .msg (Outlook) 文件走同一端点
curl -X POST "http://localhost:8036/extract/eml" \
  -F "file=@phishing.msg"

# 显式指定标签 / 模型
curl -X POST "http://localhost:8036/extract/eml" \
  -F "file=@phishing.eml" \
  -F 'labels=["邮箱","域名","URL","IP","哈希"]' \
  -F "model_name=iocextract"
```

错误示例：

```json
// 400 — 扩展名不支持
{ "detail": "不支持的文件类型 '.txt',仅支持 .eml / .msg 邮件文件" }

// 400 — 非法邮件内容
{ "detail": "未能从文件中解析出邮件内容,请确认是合法的 EML 文件" }
```

### 4.3. 查询任务结果

查询任务的执行结果和实体统计信息。

#### 4.3.1. 请求信息

- **URL**: `/tasks/{task_id}/result`
- **Method**: `GET`
- **URL 参数**: `task_id` - 任务 ID（从提交接口获取）

#### 4.3.2. 响应参数

| 参数名 | 类型 | 说明 |
|--------|------|------|
| `status` | integer | 任务状态：`1`=成功，`0`=进行中，`-1`=失败 |
| `msg` | string | 状态消息，如 "任务执行成功"、"任务执行中"、"任务执行失败: xxx" |
| `task_id` | string | 任务 ID |
| `model_name` | string | 使用的模型名称 |
| `latency_ms` | float | 模型推理耗时（毫秒） |
| `entities` | array | 提取到的实体列表 |
| `entity_stats` | object | 实体类型统计 |
| `label_mapping` | object | 标签映射字典（如果提交时提供） |
| `input_text` | string | 原始输入文本（不含标记，字符偏移与 `entities` 的 start/end 对齐） |
| `mark_text` | string | 整篇文本，每个实体用 `⟦label⟧...⟦/label⟧` 包裹（类 XML 标记）；任务未成功时为 `null` |
| `labels` | array | 提交的标签列表 |
| `information_json` | object | 用户自定义信息（原封不动返回） |

#### 4.3.3. entities 数组元素结构

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `text` | string | 实体文本 |
| `label` | string | 标准标签（映射后） |
| `raw_label` | string | 原始标签（映射前），如果未使用映射则为 null |
| `start` | integer | 实体在文本中的起始位置 |
| `end` | integer | 实体在文本中的结束位置 |
| `score` | float | 置信度分数（0-1） |
| `model_name` | string | 产出该实体的模型名称；`auto` 自动路由模式下为实际命中的子模型名 |
| `marked_context` | string \| null | 该实体所在的上下文片段，实体本身用 `⟦label⟧...⟦/label⟧` 包裹。上下文边界先保证实体前/后各至少 `MARK_CONTEXT_MIN_BEFORE` / `MARK_CONTEXT_MIN_AFTER` 个字符，再继续向前/向后找到第一个分隔符才切断；无原文或越界时为 `null` |
| `chunk_index` | integer \| null | 产出该实体的 Chunk 序号(0 起);历史任务 / UIE 降级任务为 `null` |
| `chunk_char_start` | integer \| null | 所属 Chunk 在原文中的起始字符偏移 |
| `chunk_char_end` | integer \| null | 所属 Chunk 在原文中的结束字符偏移 |
| `technique_id` | string \| null | **仅 `attack` 类模型（`tram` / `attack-llm`）**：ATT&CK 技术编号，如 `T1059.003`。其它模型为 `null` |
| `technique_name` | string \| null | ATT&CK 技术名称（来自 `models/attack/techniques.json` 富化），如 `Windows Command Shell` |
| `tactics` | array[string] \| null | 该技术所属战术 shortname 列表，如 `["execution", "persistence"]` |
| `technique_url` | string \| null | ATT&CK 官方技术页面 URL |
| `is_subtechnique` | boolean \| null | 是否为子技术（编号带 `.xxx`） |
| `parent_technique` | string \| null | 父技术编号（子技术才有），如 `T1059.003` → `T1059` |

> **ATT&CK 富化字段**：以上 6 个 `technique_*` / `tactics` / `parent_technique` 字段只有 `attack` 类模型会填充，其它 NER / IOC 模型均为 `null`（向后兼容）。它们会持久化并随 `/tasks/{task_id}/result`、`/tasks/{task_id}` 与回调 Payload 一起返回。

#### 4.3.4. chunk_metadata 响应字段(long-text-chunking-ner)

`/tasks/{task_id}/result` 与 `/tasks/{task_id}` 的成功响应、回调 Payload 里都新增一个 `chunk_metadata` 字段。未分块 / 历史任务时为 `null`。

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `chunking_enabled` | boolean | 本次请求是否真的执行了分块(`false` 表示降级或未启用)|
| `model_max_tokens` | integer \| null | 模型 tokenizer 硬上限(`gliner_multi-v2.1` = 384,`gliner-x-large` = 1024,UIE = `null`)|

| `effective_max_tokens` | integer \| null | 单块允许的 token 上限 = `model_max_tokens − labels_token_count − safety_margin` |
| `overlap` | integer | 本次生效的字符重叠数 |
| `safety_margin` | integer | 本次生效的 token 安全余量 |
| `threshold` | float | 本次生效的 `predict_entities` threshold |
| `chunk_count` | integer | Chunk 总数(≥ 0)|
| `chunks` | array | 每个 Chunk 的明细,见下方 |

#### 4.3.5. chunks 数组元素结构

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `chunk_index` | integer | 块序号,从 0 起单调递增 1 |
| `char_start` | integer | 在原文中的起始字符偏移(闭)|
| `char_end` | integer | 在原文中的结束字符偏移(开)|
| `char_length` | integer | `char_end − char_start` |
| `token_count` | integer \| null | tokenizer 编码后的 token 数;UIE 降级时为 `null` |
| `status` | string | `done` 或 `failed`(单块推理异常只影响本块,不影响整个任务)|

### 4.7. 获取模型列表

获取当前可用的模型列表。

#### 4.7.1. 请求信息

- **URL**: `/models`
- **Method**: `GET`

#### 4.7.2. 响应参数

| 参数名 | 类型 | 说明 |
|--------|------|------|
| `models` | array[string] | 可用模型名称列表 |
| `models_info` | array[object] | 每个模型的详情，元素形如 `{"name": "tram", "type": "attack"}`。`type` 取值：`ner`（GLiNER/UIE 等）、`ioc`（ioc-finder/iocextract）、`auto`（智能分流）、`llm`（通用大模型）、`attack`（TRAM / attack-llm）。前端据此把模型分到「NER 调用台」与「ATT&CK 调用台」 |

#### 4.7.3. 响应示例

```json
{
  "models": [
    "gliner-x-large",
    "ioc-finder",
    "iocextract",
    "tram",
    "auto"
  ],
  "models_info": [
    { "name": "gliner-x-large", "type": "ner" },
    { "name": "ioc-finder",     "type": "ioc" },
    { "name": "iocextract",     "type": "ioc" },
    { "name": "tram",           "type": "attack" },
    { "name": "auto",           "type": "auto" }
  ]
}
```

> 实际返回的模型取决于 `.env` 的两份清单 `NER_MODELS_ENABLED` / `ATTACK_MODELS_ENABLED`（详见 [7.6 启用的模型](#76-启用的模型)）。大模型（LLM）在 NER 台以 `type=llm` 出现、在 ATT&CK 台以 `type=attack` 出现；同一 LLM 同时进两个台时，ATT&CK 实例的 `name` 会带 `-attack` 后缀。

#### 4.7.4. 模型说明

| 模型名称 | 语言支持 | 类型 | 推荐场景 |
|----------|----------|------|----------|
| `gliner-x-large` | 多语言 | ner | 高精度实体抽取 |
| `gliner_multi-v2.1` | 多语言（推荐中文） | ner | 中文实体提取 |
| `UIE-base` | 中文 | ner | 通用中文场景 |
| `UIE-micro` | 中文 | ner | 快速响应场景 |
| `ioc-finder` / `iocextract` | 无关 | ioc | 确定性 IOC 抽取（IP/域名/URL/哈希/CVE…） |
| `tram` | 英文（CTI 报告） | attack | MITRE ATT&CK 技战术识别（SciBERT，约 440MB，固定 50 类技术） |
| `attack-llm`（配置后出现） | 中 / 英 | attack | MITRE ATT&CK 技战术识别（大模型推断，覆盖全部 600+ 技术） |

#### 4.7.5. ATT&CK 技战术识别（`tram` / `attack-llm`）

`attack` 类模型（`tram`、`attack-llm`）与其它「实体抽取」模型定位不同——它们从威胁报告文本中识别其描述的 **MITRE ATT&CK 技术**（即使原文没有显式写出技术编号），把命中的片段作为「实体」返回：

- `text`：命中的原文片段；`start` / `end`：其字符偏移；
- `label`：ATT&CK 技术编号（如 `T1059.003`）；`score`：置信度；
- 富化字段：`technique_id` / `technique_name` / `tactics` / `technique_url` / `is_subtechnique` / `parent_technique`（来自 `models/attack/techniques.json`），随结果与回调一并返回（见 [4.3.3 entities 结构](#3-查询任务结果)）。

**两个模型的区别**

| 模型 | 原理 | 语言 | 覆盖 |
|------|------|------|------|
| `tram` | MITRE TRAM 的 SciBERT **句子级多标签分类器**：按句子切分文本，逐句 `sigmoid` 判定其命中的技术，命中同一技术的句子按区间返回 | 英文效果好 | 固定 **50** 类常见技术 |
| `attack-llm` | 大模型按提示词从行为叙述**推断**技术编号，并用 `techniques.json` 校验（丢弃幻觉编号）+ 富化 | **中 / 英文** | 全部 **600+** 技术 |

**full（全量）/ 过滤模式** —— 两个模型语义完全一致，由请求的 `labels` 决定：

- **全量模式（默认，推荐）**：`labels` 里没有可识别的技术编号 / 战术时，返回全部命中的技术。为满足接口 `labels` 必填约束，直接填哨兵词即可，如 `["full"]`、`["ATT&CK"]`、`["技战术"]`，甚至任意语义词都会走全量。
- **过滤模式**：`labels` 里包含技术编号或战术 shortname 时，只返回匹配项：
  - 技术编号：`T1059`（父编号，匹配其全部子技术）或 `T1059.003`（精确子技术）；
  - 战术：`execution` / `persistence` 等 shortname（大小写、空格、连字符不敏感）。
  - 例：`"labels": ["T1059", "T1566", "execution"]`。

`threshold`（请求体，默认 0.5）作为命中阈值对两个模型都生效。`label_mapping` 仍会在上层对返回的技术编号做映射（一般无需使用）。

**启用方式**

- `tram`：先运行 `python benchmark/download_tram.py` 下载模型到 `models/tram/`，再在 `.env` 的 `ATTACK_MODELS_ENABLED` 中加入 `tram`。
- `attack-llm`（大模型映射）：在 `ATTACK_MODELS_ENABLED` 里引用某个 LLM——组别名（如 `LLM_MODELS_1`）或模型名（如 `glm-5`），连接自动从对应 `LLM_*` 组解析（见 [7.6 启用的模型](#76-启用的模型)）。
- 富化数据：运行 `python benchmark/download_attack_data.py` 生成 `models/attack/techniques.json`（缺失时技术编号仍返回，但没有名称 / 战术 / URL）。

## 5. 分块功能（long-text-chunking-ner）

为什么需要分块：GLiNER 系列模型的 tokenizer 有硬性长度上限（`gliner_multi-v2.1` = 384、`gliner-x-large` = 1024 token），超过上限时底层会**静默截断**尾部文本，导致长文本后半段的实体全部丢失。

分块功能默认启用（`CHUNK_ENABLED=true`），全流程如下：

1. **按句切分**：按中英文断句符（`。？！；…. ?!;` + 换行）把原文切成若干句。支持英文缩写保护（`Mr. / Dr. / e.g. / U.S.` 等不断）、版本号保护（`1.2.3` 不断）。
2. **贪心打包**：把相邻句子合并到一个 Chunk，直到再加一句就会超过 `effective_max_tokens` 上限。
3. **字符级回退**：单句过长时按字符切分；每步都用模型真实 tokenizer 校验 token 数。
4. **重叠区**：相邻 Chunk 保留 `chunk_overlap` 字符的重叠，避免实体被切在边界。
5. **独立推理 + 合并去重**：每个 Chunk 独立调用 `predict_entities`，把局部 offset 加上 `chunk.char_start` 得到全局 offset；重叠区的同 `raw_label` 实体按 `(score↓, chunk_index↑, length↓, 原序↑)` 四级规则去重。

### 5.1. 关键公式

```
effective_max_tokens = model_max_tokens − labels_token_count − safety_margin
```

- `model_max_tokens`：模型硬上限（384 或 1024）
- `labels_token_count`：labels 按 `<<ENT>>label<<SEP>>` 编码后的 token 总数
- `safety_margin`：安全余量（默认 16），防止 tokenizer 边界情况超限

### 5.2. 降级路径

| 场景 | 表现 |
|---|---|
| `chunk_enabled=false` | 整段文本作单 Chunk 送模型，`chunking_enabled=false` |
| 指定 UIE 模型 | 自动降级，`model_max_tokens=null`、`chunking_enabled=false` |
| `effective_max_tokens < 50` | 视为窗口过小，降级单块，日志打 `chunking skipped: effective_max_tokens too small` |
| `effective_max_tokens ≤ 0` | labels 爆容，任务 `failed`，`error_msg: "模型容量配置异常..."` |
| 单个 Chunk 推理异常 | `chunk_metadata.chunks[k].status=failed`，其他块照常，任务仍 `done` |
| 所有 Chunk 都推理失败 | 任务 `failed`，`error_msg: "所有分块推理均失败"` |

### 5.3. 缓存与分块参数

四个分块参数（`chunk_enabled / chunk_overlap / chunk_safety_margin / threshold`）都会纳入 `compute_task_hash`：

```
task_hash = md5(text + sorted(labels) + model_name + chunk_cfg)
```

即不同分块参数对应不同缓存记录，不会错误命中。

## 6. 回调功能

### 6.1. 回调概述

回调功能允许任务完成后自动将结果推送到用户指定的 URL，无需轮询查询。

**工作流程**：
1. 提交任务时携带 `callback` 参数
2. 任务提取完成后，结果自动放入回调队列
3. 回调线程池发送 HTTP 请求到指定 URL
4. 成功则记录日志，失败则写入失败记录表
5. 用户可在管理界面查看失败记录并手动重试

**注意事项**：
- 回调功能默认不启用，需在 `.env` 中设置 `CALLBACK_ENABLED=true`
- 回调失败不会自动重试，需手动操作
- 不配置 `callback` 参数时，行为与原来完全一致（通过轮询查询结果）
- 配置回调后仍可通过 `/tasks/{task_id}/result` 查询结果（双保险）

**回调请求体格式**（发送到用户 URL 的数据）：

```json

      "label": "PERSON",
      "raw_label": "人物",

      "end": 2,
      "score": 0.95,
      "model_name": "gliner_multi-v2.1",
      "marked_context": "⟦PERSON⟧张三⟦/PERSON⟧在北京创办了一家科技公司，主要研发人工智能产品。",
```

## 7. 环境变量配置

所有后端行为都可通过 `api/.env` 文件调整,热更新需重启 uvicorn。

### 7.1. 文本与文件输入

| 环境变量 | 默认值 | 作用 |
|----------|--------|------|
| `MAX_TEXT_LENGTH` | `50000` | `POST /extract` 的 JSON `text` 字段上限（字符数）。超出返回 **413**，提示改用 `/extract/upload` |
| `UPLOAD_MAX_BYTES` | `10485760`(10 MB) | `POST /extract/upload` 的单文件字节上限。超出返回 **400** |
| `UPLOAD_ALLOWED_EXTENSIONS` | `.txt,.md,.markdown,.rst,.log,.csv,.tsv,.json,.jsonl,.ndjson,.xml,.yaml,.yml,.ini,.cfg,.toml,.html,.htm,.srt,.vtt` | 上传文件扩展名白名单（逗号分隔，含点号）。修改此项时请同步前端 `ALLOWED_TEXT_EXTENSIONS` 常量 |

> **两者是独立的限制维度**:`MAX_TEXT_LENGTH` 仅对 JSON 接口生效,`UPLOAD_MAX_BYTES` 仅对文件上传接口生效。文件解码为字符串后不会再触发 `MAX_TEXT_LENGTH` 的 413 检查。

### 7.2. 分块

| 环境变量 | 默认值 | 作用 |
|----------|--------|------|
| `CHUNK_ENABLED` | `true` | 默认是否启用长文本分块。请求体 `chunk_enabled` 可单次覆盖 |
| `CHUNK_OVERLAP` | `32` | 相邻 Chunk 字符重叠数，范围 `[0, 512]` |
| `CHUNK_SAFETY_MARGIN` | `16` | `effective_max_tokens` 的 token 安全余量，范围 `[0, 64]` |
| `CHUNK_THRESHOLD` | `0.5` | `predict_entities` 的默认阈值，范围 `[0.0, 1.0]` |

### 7.3. 实体标记上下文

结果中除原始 `input_text` 外，额外提供带标记字段 `mark_text`（整篇）与每个实体的 `marked_context`（上下文片段），实体用 `⟦label⟧...⟦/label⟧` 包裹。`input_text` 与实体 `start/end` 偏移保持不变，完全向后兼容。

| 环境变量 | 默认值 | 作用 |
|----------|--------|------|
| `MARK_CONTEXT_MIN_BEFORE` | `30` | `marked_context` 中实体**前方**至少截取的字符数 |
| `MARK_CONTEXT_MIN_AFTER` | `30` | `marked_context` 中实体**后方**至少截取的字符数 |
| `MARK_CONTEXT_SEPARATORS` | `。！？；!?;\n` | 分隔符集合，值中每个字符各算一个分隔符，支持 `\n` `\r` `\t` 转义 |

> **截取逻辑**：上下文边界不是固定字符数硬切。以实体为中心，先向前/向后各保证至少 `MIN_BEFORE` / `MIN_AFTER` 个字符，然后从该位置继续向前/向后扫描，直到遇到第一个分隔符才真正切断（向前切在分隔符之后，向后把句末分隔符一并保留）。这样能尽量保留完整句子。当实体区间非法或无原文时，`marked_context` 为 `null`。整篇 `mark_text` 在实体区间重叠时只保留靠前的实体标记，避免标记交叉。

### 7.4. 任务队列

| 环境变量 | 默认值 | 作用 |
|----------|--------|------|
| `WORKER_THREADS` | `6` | 推理线程池大小 |
| `MAX_QUEUE_SIZE` | `500` | 队列最大长度。队列满时 `POST /extract` 返回 **503** |

### 7.6. 启用的模型（按调用台分两份清单）

模型按调用台组织成两份清单，每份都可**混选专有模型与 LLM**：

| 环境变量 | 默认值 | 作用 |
|----------|--------|------|
| `NER_MODELS_ENABLED` | `gliner-x-large,ioc-finder,iocextract,auto` | 「NER 调用台」可选模型清单，逗号分隔 |
| `ATTACK_MODELS_ENABLED` | `tram` | 「ATT&CK 调用台」可选模型清单，逗号分隔 |

**清单条目的三种写法**

| 写法 | 示例 | 含义 |
|------|------|------|
| 专有模型名 | `gliner-x-large` / `ioc-finder` / `iocextract` / `UIE-base` / `auto` / `tram` | 内置注册表模型。`tram` 属 ATT&CK 台，`auto` 仅 NER 台有效 |
| LLM 组别名 | `LLM_MODELS_1` / `LLM_MODELS_2` / `LLM_MODELS_3` | 展开为该 `LLM_*` 组里配置的全部模型（`LLM_MODELS_1` = 第一组 `LLM_MODELS`） |
| LLM 模型名 | `glm-5` | 直接写模型名，自动定位它所在的 `LLM_*` 组并取其连接配置 |

- **LLM 在哪个台，就用哪套 prompt**：出现在 `NER_MODELS_ENABLED` → 包成 NER 抽取器（按 `labels` 抽实体，`type=llm`）；出现在 `ATTACK_MODELS_ENABLED` → 包成 ATT&CK 映射器（从行为叙述推断技术编号，`type=attack`）。
- **同一个 LLM 同时进两个台**：直接在两份清单里都写它。NER 实例键为 `<模型名>`，ATT&CK 实例自动登记为 `<模型名>-attack`（`model_name` 不歧义、缓存天然隔离）。真实 API 模型名不变，前端各台下拉各显示各的，无需手敲后缀。
- **LLM 连接定义**仍由 `LLM_*` 组提供（`LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODELS` / `LLM_TEMPERATURE` / `LLM_TIMEOUT` / `LLM_HEADERS`，及 `_2` / `_3` 组）。两个台共用这些连接组。

> **向后兼容**：当 `NER_MODELS_ENABLED` 与 `ATTACK_MODELS_ENABLED` **都留空**时，自动回退到旧逻辑——`MODELS_ENABLED`（专有 + tram）+ `LLM_MODELS*`（全部当 NER）。历史部署无需改配置即可运行；但旧路径不加载 attack-llm，如需大模型 ATT&CK 映射请改用上面两份清单。

**LLM 连接组（NER / ATT&CK 共用）**

| 环境变量 | 默认值 | 作用 |
|----------|--------|------|
| `LLM_MODELS`（及 `_2` / `_3`） | 空 | 该组提供连接的 LLM 模型名列表（逗号分隔） |
| `LLM_BASE_URL`（及 `_2` / `_3`） | 见 .env | OpenAI 兼容 API base URL（不含 `/chat/completions`） |
| `LLM_API_KEY` / `LLM_TEMPERATURE` / `LLM_TIMEOUT` / `LLM_HEADERS`（及 `_2` / `_3`） | — | 该组的鉴权 / 采样 / 超时 / 自定义头 |

**TRAM（`attack` 类，SciBERT）**

| 环境变量 | 默认值 | 作用 |
|----------|--------|------|
| `TRAM_MAX_LENGTH` | `256` | tokenizer 截断长度 |
| `TRAM_BATCH_SIZE` | `16` | 句子批量推理的批大小 |
| `TRAM_MIN_SENT_CHARS` | `3` | 参与分类的句子最小非空白字符数（更短的碎片跳过） |
| `TRAM_DEVICE` | 空（自动） | 强制推理设备 `cuda` / `mps` / `cpu`，留空自动选择 |

**attack-llm（`attack` 类，大模型 ATT&CK 映射）**

不需要独立的连接变量：在 `ATTACK_MODELS_ENABLED` 里引用某个 LLM（组别名 `LLM_MODELS_1` 等，或模型名如 `glm-5`）即可，连接自动复用对应 `LLM_*` 组。该 LLM 会以 ATT&CK 映射器（`type=attack`）身份出现在 ATT&CK 调用台。

> 富化数据 `models/attack/techniques.json` 由 `python benchmark/download_attack_data.py` 生成，供 `tram` 与大模型 ATT&CK 映射共用（`tram` 富化技术编号；大模型路径额外用它校验、丢弃幻觉编号）。

### 7.7. 认证

| 环境变量 | 默认值 | 作用 |

| `AUTH_ENABLED` | `true` | 是否启用认证。设为 `false` 时所有接口免认证访问（内部以虚拟 admin 身份运行，且不做限额） |
| `JWT_SECRET_KEY` | `ner-api-jwt-secret-change-this-in-production-2026` | JWT 签名密钥，**生产环境务必修改并保密** |

## 8. 错误码说明

### 8.1. HTTP 状态码

| 状态码 | 触发场景 |
|--------|---------|
| 200 | `GET` 请求成功 |
| 202 | 任务已接受并入队（异步处理） |
| 400 | 请求参数错误，或上传文件未通过格式/大小/二进制特征校验 |
| 401 | 未认证。未提供凭证，或 API Key / JWT Token 无效、已过期、已停用 |
| 403 | 拒绝访问。账户已被停用，或普通用户访问了需要管理员权限的接口 |
| 404 | 资源不存在（task_id / 失败记录 id 不存在） |
| **413** | `/extract` 的 `text` 长度超过 `MAX_TEXT_LENGTH`。响应 `detail` 会明确指示改用 `/extract/upload` |
| 422 | pydantic 字段校验失败:`text` 空字符串、`chunk_overlap` / `chunk_safety_margin` / `threshold` 越界、`labels` 为空数组、`/extract/upload` 的表单 JSON 字段格式错误等 |
| 429 | 超出调用限额（5 小时或每周），仅 `POST /extract`、`POST /extract/upload` 会触发 |
| 503 | 服务不可用(队列满或模型未加载) |

### 8.2. 分块相关错误

| 触发条件 | 表现 |
|----------|------|
| `chunk_overlap` 不在 `[0, 512]` / `chunk_safety_margin` 不在 `[0, 64]` / `threshold` 不在 `[0.0, 1.0]` | 422,字段级错误信息 |
| `labels_token_count + safety_margin ≥ model_max_tokens` (即 `effective_max_tokens ≤ 0`) | 任务 `status=failed`,`error_msg: "模型容量配置异常..."` |
| 个别 Chunk 推理异常(并非全部失败) | 任务仍 `status=done`,`chunk_metadata.chunks[k].status=failed` 并带 `error` 摘要,其他 Chunk 实体正常返回 |
| 所有 Chunk 都推理失败 | 任务 `status=failed`,`error_msg: "所有分块推理均失败"` |

### 8.3. 文件上传相关错误

| 触发条件 | HTTP 码 | 响应 detail |
|----------|---------|-------------|
| 空文件 | 400 | `上传文件为空` |
| 超过 `UPLOAD_MAX_BYTES` | 400 | `上传文件过大 (N 字节),上限 M 字节` |
| 扩展名不在白名单 | 400 | `不支持的文件类型 '.xxx'。仅支持纯文本格式: ...` |
| 头部字节特征是二进制 | 400 | `文件内容看起来不是纯文本(检测到二进制特征),请上传真实文本文件` |
| 编码解析失败 | 400 | `文件解码失败: ...` |
| 解码后内容为空白 | 400 | `文件内容为空白` |
| 表单 JSON 字段格式错误 | 422 | `表单字段 xxx 不是合法 JSON: ...` |

### 8.4. 业务状态码(`status` 字段)

#### 8.4.1. Stage 1 (提交任务 - ExtractResponse.code)

| code | status | 说明 |
|------|--------|------|
| 200 | "成功" | 任务提交成功(202 响应的响应体里 `code=200`) |

## 9. iframe 嵌入集成（页面可视化）

系统提供了一个无导航条、无侧边栏历史列表的纯净版“实体提取可视化”页面，方便其他系统直接通过 `<iframe>` 标签集成特定的实体识别任务展示。

### 9.1. 访问 URL 格式

集成页面支持以下两种 URL 访问方式（开发环境和生产环境均适用）：

#### 9.1.1. 方式 A：Path 路由（推荐）
```
http://{your-server}:{port}/iframe/{task_id}
```
*示例*：
```
http://localhost:8036/iframe/15c2eff1-d1d5-42f7-b822-65195892a201
```

#### 9.1.2. 方式 B：Hash 路由（兼容）
```
http://{your-server}:{port}/#/iframe/{task_id}
```
*示例*：
```
http://localhost:5466/#/iframe/15c2eff1-d1d5-42f7-b822-65195892a201
```

### 9.2. 集成特点
- **隐藏导航与头部**：页面顶部的 `NER API Dashboard` 导航栏被自动隐藏。
- **隐藏左侧任务列表**：隐藏了“历史任务”面板，只展示当前任务的提取可视化详情。
- **隐藏查询输入框**：由于 Task ID 已通过 URL 绑定，输入查询框会被隐藏，确保界面的专注与整洁。
- **自适应布局**：右侧的可视化详情面板采用无边框、无阴影、紧凑内边距设计（`.iframe-view`），支持响应式缩放，完美企合 `<iframe>` 的宽度和高度。
- **优化加载**：iframe 模式下将不会从后端拉取历史任务列表，减少服务端的数据库和网络开销。

### 9.3. 集成 HTML 示例

使用标准的 HTML `<iframe>` 标签即可将特定任务的可视化部分嵌入到第三方系统中：

```html
<iframe 
  src="http://localhost:8036/iframe/15c2eff1-d1d5-42f7-b822-65195892a201" 
  width="100%" 
  height="800px" 
  frameborder="0" 
  allowfullscreen
></iframe>
```

### 9.4. 页面打开功能
为了方便调试，在原版的“实体可视化”面板中，如果当前输入框中有 Task ID，会在“查询”按钮旁动态显示 **“打开集成页面 ↗”** 按钮。点击该按钮可以直接在新标签页中以 iframe 纯净模式打开当前任务的可视化页面。

### 9.5. URL 携带账号密码免登录（自动登录）

当其他系统通过 `<iframe>` 集成本平台时，往往希望跳过登录页直接进入。可在访问页面的 URL 上附带账号与密码查询参数，前端会在加载时自动调用登录接口完成登录。

#### 9.5.1. URL 格式
```
http://{your-server}:{port}/?user={用户名}&password={密码}
```
*示例*：
```
http://localhost:5466/?user=admin&password=12345679
```

也可与 iframe 可视化路由（见 9.1）组合使用，先自动登录再展示指定任务：
```
http://localhost:5466/?user=admin&password=12345679#/iframe/15c2eff1-d1d5-42f7-b822-65195892a201
```

#### 9.5.2. 参数说明

| 参数 | 别名 | 必填 | 说明 |
|------|------|------|------|
| `user` | `username` | 是 | 登录用户名 |
| `password` | `pwd` | 是 | 登录密码 |

> 两个参数需同时提供才会触发自动登录。两种参数名（如 `user` 与 `username`）等价，任选其一即可。

#### 9.5.3. 行为说明
- **自动登录**：页面加载时若检测到 `user` 与 `password` 参数且当前尚未登录，会自动调用 `POST /auth/login` 获取 JWT 并保存到本地，登录成功后直接进入仪表盘 / iframe 视图。
- **加载态**：自动登录过程中显示“正在登录…”加载动画，避免登录页一闪而过。
- **URL 自动清理**：无论登录成功或失败，登录流程结束后都会立即从地址栏移除 `user`、`password` 等凭据参数（通过 `history.replaceState`），避免账号密码残留在浏览器历史或被作为 Referer 泄露。页面的 hash 路由（如 `#/iframe/{task_id}`）会被保留。
- **已登录跳过**：若浏览器本地已存在有效登录态，则不会重复登录，仅清理 URL 中的凭据参数。
- **登录失败**：凭据错误时自动登录静默失败（控制台输出错误信息），并回退到正常登录页，用户可手动登录。

#### 9.5.4. iframe 集成示例
```html
<iframe
  src="http://localhost:5466/?user=admin&password=12345679#/iframe/15c2eff1-d1d5-42f7-b822-65195892a201"
  width="100%"
  height="800px"
  frameborder="0"
  allowfullscreen
></iframe>
```

> **安全提示**：URL 中的账号密码为明文，存在被浏览器历史、服务器访问日志、Referer 头记录的风险。建议：
> - 仅在受信任的内网或安全的集成环境中使用；
> - 优先为集成方分配权限受限的专用账号；
> - 全程使用 HTTPS 传输；
> - 如对安全性要求更高，建议改用 API Key 方式（见 3.1）由后端代理调用，而非在前端 URL 暴露凭据。

### 10.1. cURL 示例

> **注意**：除公开接口（`/auth/login`、`/models`、`/server-info` 等）外，所有调用都需认证。以下示例采用 `X-API-Key` 方式，也可换成 `Authorization: Bearer <Token>`。

### 10.2. JavaScript 示例

```javascript
const BASE_URL = "http://localhost:8036";
const API_KEY = "ner_your_api_key_here"; // 你的 API Key

// 统一构造带认证的请求头
const getHeaders = (extra = {}) => ({
  "X-API-Key": API_KEY,
  "Content-Type": "application/json",
  ...extra
});

// Step 1: 提交任务
async function submitTask() {
  const response = await fetch(`${BASE_URL}/extract`, {
    method: "POST",
    headers: getHeaders(),
    body: JSON.stringify({
      text: "张三在北京创办了一家科技公司。",
      labels: ["人物", "地点", "机构"],
      label_mapping: { "人物": "PERSON", "地点": "LOCATION", "机构": "ORG" },
      model_name: "gliner_multi-v2.1",
      information_json: { file_id: "0537ef0d8ac6a2179a58067615825924" }
    })
  });
  
  const result = await response.json();
  if (result.code === 200) {
    console.log(`✓ 任务提交成功: ${result.task_id}`);
    return result.task_id;
  } else {
    console.error(`✗ 任务提交失败: ${result.msg}`);
    return null;
  }
}

// Step 2: 查询结果（轮询）
async function queryResult(taskId) {
  const maxRetries = 30;
  
  for (let i = 0; i < maxRetries; i++) {
    const response = await fetch(`${BASE_URL}/tasks/${taskId}/result`, {
      headers: getHeaders()
    });
    const result = await response.json();
    
    if (result.status === 1) {
      console.log(`✓ 任务完成，提取到 ${result.entities.length} 个实体`);
      return result;
    } else if (result.status === -1) {
      console.error(`✗ 任务失败: ${result.msg}`);
      return null;
    } else {
      console.log(`[${i+1}s] ${result.msg}`);
      await new Promise(resolve => setTimeout(resolve, 1000));
    }
  }
  
  console.error("✗ 查询超时");
  return null;
}

// 完整流程
(async () => {
  const taskId = await submitTask();
  if (taskId) {
    const result = await queryResult(taskId);
    if (result) {
      console.log("\n提取结果:");
      result.entities.forEach(entity => {
        console.log(`  - ${entity.text} (${entity.label}) [置信度: ${entity.score.toFixed(2)}]`);
      });
    }
  }
})();
```

## 11. 最佳实践

### 11.1. 标签设计

- **使用中文标签**：更直观，如 `["人物", "地点", "机构"]`
- **启用标签映射**：统一输出格式，如 `{"人物": "PERSON"}`
- **标签粒度适中**：不要过于细分或过于宽泛

### 11.2. 结果复用

- **启用缓存**:对于相同文本和标签的重复请求,设置 `reuse_cache: true`
- **缓存键组成**:`md5(text + sorted(labels) + model_name + chunk_cfg)`,标签顺序不影响匹配
- **文本输入与文件上传共享同一缓存**:上传文件后文件内容会被解码为文本,与直接输入文本走相同的哈希计算,内容相同即可互相命中
- **`information_json` 不参与哈希**:命中缓存时仍会用当前请求的 `information_json` 覆盖
- **缓存有效期 (TTL)**:每条缓存有过期时间,默认 8 小时,超期后不再被复用(任务记录本身仍可通过 `GET /tasks/{id}/result` 查询)。
- **命中刷新策略**:默认开启「滑动过期」——命中缓存会把过期时间重置为 `当前时间 + TTL`,热点结果可长期保活。
- **后台自动清理**:服务内置定时任务,默认每 1 小时物理删除一次已过期的缓存任务行(防止数据库膨胀)。可在 `api/.env` 中通过 `CACHE_CLEANUP_ENABLED` / `CACHE_CLEANUP_INTERVAL` 配置开关与间隔。仅删除已过期的缓存任务,不影响历史任务和未启用复用的任务。
- **全局策略可调**:管理员可在 Dashboard「管理 → 缓存管理」页调整总开关 / TTL / 命中刷新,并可查看缓存条目、清理过期或全部缓存。页面分 NER / ATT&CK / 联网解析三类:NER 与 ATT&CK 共用本策略,统计/条目/清理按模型类型分开;联网解析缓存策略独立(见《联网情报手册》)。对应接口见下:

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/admin/cache/settings` | 读取缓存策略 |
| PUT | `/admin/cache/settings` | 更新策略(`enabled` / `ttl_seconds` / `refresh_on_hit`) |
| GET | `/admin/cache/stats` | 缓存概览(可复用 / 已过期数量),支持 `?category=ner\|attack\|ti` |
| GET | `/admin/cache/entries` | 分页查看缓存条目,支持 `?category=`(TI 条目带 platform/seed_type/seed_value) |
| DELETE | `/admin/cache/entries/{task_id}` | 使单条缓存失效(提取 / TI 任务均可) |
| POST | `/admin/cache/clear-expired` | 清理已过期缓存,支持 `?category=` 限定分类 |
| POST | `/admin/cache/clear-all` | 清空全部缓存复用,支持 `?category=` 限定分类 |

`category` 不传时为提取缓存全量(旧行为);NER / ATT&CK 分类按已加载模型的 `model_type` 划分。

### 11.3. 自定义信息绑定

- **使用 information_json**：绑定文件 ID、用户 ID、请求时间等信息
- **原封不动返回**：方便追踪请求来源和关联业务数据

### 11.4. 错误处理

- **检查 HTTP 状态码**：确保请求成功
- **检查业务状态码**：Stage 1 检查 `code`，Stage 2 检查 `status`
- **轮询超时**：建议设置最大轮询次数，避免无限等待

### 11.5. 性能优化

- **选择合适的模型**：根据精度和速度需求选择
- **批量处理**：对于大量文本，可以并发提交多个任务
- **监控队列**：通过 `/stats` 接口监控队列大小

## 12. 常见问题

### 12.1. Q1: 任务一直处于 pending 状态？

**A**: 可能原因：
- 队列已满，等待其他任务完成
- 模型加载中
- 检查 `/stats` 接口查看队列大小

### 12.2. Q2: 如何提高提取准确率？

**A**: 建议：
- 使用更大的模型（如 gliner-x-large）
- 提供更精确的标签定义
- 使用 label_mapping 统一标签格式

### 12.3. Q3: information_json 有什么用？

**A**: 用途：
- 绑定业务数据（文件 ID、用户 ID 等）
- 追踪请求来源
- 关联上下文信息
- 会在结果中原封不动返回

### 12.4. Q4: 缓存复用的匹配规则？

**A**: 匹配条件：
- 相同的文本内容
- 相同的标签列表（顺序无关）
- 相同的模型
- 返回历史提取实体最多的结果

### 12.5. Q5: 如何删除历史任务？

**A**: 使用删除接口：
```bash
curl "http://localhost:8036/tasks/{task_id}?action=delete"
```

### 12.6. Q6: 回调功能如何使用？

**A**: 在提交任务时添加 `callback` 参数：
```json
{
  "text": "...",
  "labels": ["..."],
  "callback": {
    "url": "https://your-server.com/callback"
  }
}
```
任务完成后会自动 POST 结果到指定 URL。不配置 `callback` 时行为不变。

### 12.7. Q7: 回调失败了怎么办？

**A**: 回调失败不会自动重试。可以：
1. 在管理界面"回调结果 → 回调失败"中查看失败原因
2. 点击"重试"按钮手动重试
3. 使用 API：`POST /callback/retry/{id}`
4. 失败记录会保留完整的请求头和请求体，方便排查

### 12.8. Q8: 如何测试回调地址是否可用？

**A**: 使用测试接口：
```bash
curl -X POST "http://localhost:8036/callback/test" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://your-server.com/callback"}'
```
会返回连通性、响应时间和状态码。

### 12.9. Q9: 调用接口返回 401 / 403 / 429 怎么办？

**A**:
- **401 未认证**：没带认证头，或 `X-API-Key` / `Bearer Token` 无效、过期、被停用。检查请求头是否正确，必要时重新登录或换一个有效的 API Key。
- **403 拒绝访问**：账户被停用（联系管理员启用），或普通账户访问了 `/admin/*` 等管理员接口。
- **429 超出限额**：5 小时或每周调用次数达上限。等窗口滚动后重试，或请管理员调高 `limit_5h` / `limit_weekly`。可用 `GET /auth/me` 查看当前用量。

### 12.10. Q10: API Key 和用户名密码（JWT）该用哪个？

**A**:
- **脚本 / 服务端集成**：用 **API Key**（`X-API-Key`）。它长期有效（自定义过期天数）、不需登录换取，适合自动化。
- **Web 前端 / 临时交互**：用 **用户名密码登录**换取 JWT（`Authorization: Bearer`），Token 默认 24 小时过期。
- 两种方式额度都计入同一账户，互不冲突。

### 12.11. Q11: 如何提取大文档(比如几万字的文章)的实体?

**A**: 用文件上传接口 `POST /extract/upload`:

- JSON 接口 `POST /extract` 的 `text` 字段上限默认 50,000 字符(`MAX_TEXT_LENGTH` env 可配),超过返回 413
- 上传文件接口单文件上限 10 MB(`UPLOAD_MAX_BYTES` env 可配),覆盖绝大多数长文档场景
- 支持格式:`.txt / .md / .csv / .json / .log / .xml / .yaml` 等纯文本
- 自动识别编码:UTF-8 / UTF-16 / GB18030,BOM 会被自动剥离
- 二进制文件(docx / pdf / zip 等)会被拒绝
- 文件上传后走完全相同的分块 / 缓存 / 回调流程,响应格式与 JSON 接口一致
- **文本内容相同时,JSON 接口和上传接口共享同一缓存**(`task_hash` 只看解码后的字节,不看来源)

### 12.12. Q12: 为什么我提交 text 收到了 413 错误?

**A**: `text` 长度超过了 `MAX_TEXT_LENGTH`(默认 50,000 字符)。错误响应里会告诉你当前长度、上限、如何解决。两种处理方式:

1. **改用 `/extract/upload` 上传文件**(推荐,无需改部署):
   ```bash
   # 把文本存到 .txt,走上传接口(上限 10MB,约 200 万汉字)
   curl -X POST "http://localhost:8036/extract/upload" \
     -F "file=@big-doc.txt" -F 'labels=["人物","地点"]'
   ```

2. **调大 `MAX_TEXT_LENGTH`**:在 `api/.env` 里设置更大的值并重启。不推荐超过 200,000,大 JSON body 会增加 FastAPI 解析开销和 DB 存储压力。

### 12.13. Q13: 文件上传的字段为什么要 JSON 字符串?

**A**: `multipart/form-data` 协议规定每个 part 的值只能是字符串或文件,没有原生数组/对象类型。所以 `labels`、`label_mapping`、`information_json`、`callback` 这些在 JSON 接口里是原生对象的字段,在上传接口里必须序列化成 JSON 字符串:

```bash
# JSON 接口
{"labels": ["人物", "地点"]}

# 上传接口
-F 'labels=["人物","地点"]'
```

前端 UI 已自动处理这个差异,调用方手写 curl / 自己写 SDK 时需注意。
